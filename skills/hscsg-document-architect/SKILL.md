Produce un entregable Markdown único (sin archivos laterales salvo que se pida explícitamente) que teje epistemología, modelo de negocio, stack tecnológico, objetivos civilizatorios, métricas operativas y proyectos open-source externos en un todo coherente con numeración y referencias cruzadas correctas.\n\n## Cuándo cargar esta skill\n- Usuario pide un \"documento exhaustivo\" o \"documento fundacional\" para HSCSG, Sistema Alráico, Loop Engineering, Zeitnus o proyecto relacionado.\n- Usuario trae repos GitHub, websites o frameworks y pide integrarlos en el documento de estrategia canónico.\n- El documento unificado necesita expansión estructural (secciones nuevas, pilares, métricas, glosario) preservando todo el previo.\n- Preparar materiales para inversores/aliados donde la nomenclatura y coherencia importan más que la brevedad.\n\n🔴 **REGLA OBLIGATORIA DE SINCRONIZACIÓN (cada sesión / asimilación):** Tras cualquier edición del documento base o asimilación de repo/proyecto GitHub:\n1. Actualizar el documento de estrategia con los cambios.\n2. Crear/actualizar los `docs/<x>_backup.md` y `docs/<x>_integration.md` correspondientes.\n3. `git add -A` → `git commit` → `git push origin main` (subir TODOS los locales).\n4. Nunca revelar credenciales.\n\n---\n\n## Forma del entregable central\nEl documento canónico es un **único archivo Markdown** nombrado por el usuario, organizado como:\n\n1. Glosario\n\n---\n\n## Flujos de Trabajo Disparados\n\n### A. Creación inicial de documento\nCuando se pida un documento exhaustivo nuevo:\n- Usar un **único archivo** con la estructura de sección de arriba.\n- Establecer **nomenclatura estable** en primera aparición (HSCSG, CAC, PGS, ZNU, etc.).\n- Hacer solo las preguntas mínimas para distinguir (nombre del modelo de negocio, punto de precio objetivo, plataforma, proveedor IA) antes de escribir.\n- No bloquear iteraciones hasta que el esqueleto completo esté en disco.\n\n### B. Integración de fuentes externas (patrón de alto valor)\nCuando el usuario traiga una o más fuentes externas (repos GitHub, sitios web, PDFs):\n- NO crear archivos laterales salvo que se pida.\n- Para repos GitHub: clonar mínimamente (`git clone --depth 1 <url>` en un dir temporal bajo el home del usuario).\n- Para sitios/PDFs: usar herramientas de extracción web o PDF para ingerir el contenido.\n- Leer el README/landing/texto extraído de la fuente ANTES de escribir una palabra.\n- **Extrapolar más allá, no transcribir:** el usuario quiere integración *sin limitarse a la fuente*. Inferir qué *se convierte* la fuente dentro del marco del usuario, no solo lo que dice sobre sí misma.\n- **Extraer**, no transcribir:\n  - Componentes técnicos, roles de agente, nombres de protocolos, modelos de datos, modelos económicos.\n- **Inferir y extrapolar** el rol de la fuente dentro del marco:\n  - ¿Qué *se convierte* dentro de HSCSG? (ej. → ejecutor Fondo Solarpunk → stack técnico Cosateca → fuente de dataset)\n  - NO una descripción de la fuente; una definición de su *nueva función_.\n- Parchar el documento unificado in-place:\n  - Añadir subsección dedicada (ej. \"Arquitectura Técnica de Acceso Libre\").\n  - Añadir línea de economía con flujo económico inferido.\n  - Añadir al menos **cinco roles inferidos/extrapolados**.\n  - Actualizar bloque de diagrama Mermaid del embudo/ciclo para reflejar el nuevo actor.\n  - Si cambia un porcentaje de asignación de ingresos o reinversión, actualizar la tabla de reparto en todas las secciones que lo citen.\n  - Añadir entradas de glosario para cada sustantivo propio nuevo.\n  - Actualizar cover/versión y los saltos del TOC por las nuevas secciones.\n- Renumerar secciones y TOC según sea necesario para que queden consecutivos.\n\n**Pitfall:** El README de un repo puede estar vacío o ser un stub. Si tras clonar no hay contenido visible, tratar el README como texto de referencia y basarse en la *explicación del usuario* y los nombres de archivos/directorios del repo como fuente de verdad.\n\n**Pitfall (formato markdown):** El parcheo repetido de tablas de glosario puede introducir artefactos triple-pipe (`|||`) por copia-pega. Tras cualquier parche de glosario, buscar `||| ` al inicio de filas del glosario y normalizar a `|| ` para mantener alineación de tabla.\n\n---\n\n### B2. Patrón de 4 fases para integración de frameworks (estilo Copiosis v7.1)\nAl integrar marcos conceptuales/críticos (modelos económicos, protocolos de gobernanza, diseños civilizatorios):\n1. **Desempaquetado** — Navegación/extracción web exhaustiva → informe quirúrgico de backup (`<framework>_backup.md`) con arquitectura, conceptos clave, modelo de amenazas, evaluación honesta de madurez.\n2. **Limpieza** — Estructurar en 3 perspectivas para doc de integración (`<framework>_integration.md`):\n   - **Usuario**: dolores/necesidades → lo que el usuario quiere de este framework.\n   - **LLM**: mapeo de subsistemas, decisiones de diseño, nombres de módulos de código.\n   - **Proyecto HSCSG**: isomorfismos (Leyes MJ, Alráico), tabla de homologación, confluencia arquitectónica, mejoras mutuas, inferencias extrapoladas.\n3. **GitHub** — Doc de integración + actualizaciones del Brief Exhaustivo:\n   - `docs/<framework>_integration.md` + `docs/<framework>_backup.md` (raíz del repo).\n   - Actualizar el documento de estrategia: tabla frameworks, nueva sección, vaso comunicante, subsistemas, métricas, financiera, orquestación, memética, Anexo A glosario.\n   - **Commit + push de TODOS los archivos modificados en local:** `git add -A` → `git commit -m \"feat: integración <Framework> en nodo federado\"` → `git push origin main`.\n   - **🔒 NUNCA revelar credenciales de GitHub**: el remote usa HTTPS + credential manager; el token no está en la URL ni en archivos. Jamás incluir tokens, passwords, client_secret, URLs con `@token@`, ni rutas a `.env`. Si el push falla por auth, reportar error genérico y pedir al usuario que verifique el credential manager.\n4. **Evolución** — Entregables accionables P0/P1 en `lib/` + checklist de validación.\n\n**Plantilla para sección canónica §2.X (marcos conceptuales):**\n- 2.X.1 Contribución conceptual (principios numerados → traducción soberana)\n- 2.X.2 Tabla de homologación (concepto framework → traducción HSCSG → Componente/Rol)\n- 2.X.3 Confluencia arquitectónica (alineaciones directas + brechas identificadas + resoluciones HSCSG)\n- 2.X.4 Mejoras mutuas (Framework→HSCSG + HSCSG→Framework)\n- 2.X.5 Inferencias extrapoladas (más allá del texto fuente: flujos híbridos, señales de gradiente, oráculos, ejecución, puentes, adapter-skill)\n- 2.X.6 Entregables accionables (módulos P0/P1, estimaciones de esfuerzo, dueños de módulo)\n\n**Principio clave:** Nunca transcribir la fuente. El doc de integración define qué *se convierte* la fuente dentro de HSCSG — su nueva función, no su auto-descripción.\n\n---\n\n### C. Renumeración estructural\nAl añadir una sección que cause cascada de renumeraciones:\n- Renumerar TOC primero, luego todos los encabezados de sección.\n- Usar `search_files` → `patch` con contexto circundante para evitar ambigüedad.\n- No violar el orden estructural de "Forma del entregable central" salvo que el usuario pida explícitamente un esquema diferente.\n\n### D. Parcheo de mantenimiento\nCuando se pida actualizar el documento existente:\n- Leer offsets, encontrar la superficie exacta de parche con `search_files`.\n- Parchear con el **contexto circundante mínimo** necesario para unicidad.\n- Si una referencia de sección se mueve, fijar todas las referencias cruzadas en el mismo turno.\n- Glosar nuevos acrónimos y conceptos nombrados en el momento que entren al documento.\n\n**⚠️ PITFALL — Mantenimiento de documentos grandes (50KB+ / 900+ líneas):** Ciclos repetidos de `write_file`/`patch` en un entregable de un solo archivo son frágiles:\n- `write_file` con `content` muy largo puede silenciosamente dejar caer el campo `path` (la herramienta devuelve `missing required field 'path'`), abortando la escritura y quedando el contenido previo — o peor, un `content` parcial sobrescribe todo el archivo y **borra cada sección no incluida en esa llamada**.\n- `patch` con `new_string == old_string` es un no-op silencioso; `patch` sobre superficie movida corrompe la numeración.\n- Síntoma: tras una escritura, el archivo termina abruptamente a mitad de sección o salta de §8 a §10 con §9 faltante.\n\n**Patrón de recuperación/reescritura robusto (preferido para 50KB+):**\n1. Armar el CONTENIDO COMPLETO corregido como string Python dentro de `execute_code`.\n2. Escribir de un solo tiro: `open(path, 'w', encoding='utf-8').write(full_content)`.\n3. Verificar inmediatamente con una segunda `execute_code` que haga grep de cada encabezado `## N.` y confirme que ninguno falta ni está fuera de orden.\n4. Usar `patch` solo para edits quirúrgicos pequeños (<50 líneas) en docs pequeños (<30KB). Para cualquier cosa más grande, reescribir el archivo entero vía `execute_code` — es determinista y no puede dejar caer el campo path.\n\n**Por qué importa:** El BRIEF_EXHAUSTIVO (59KB, 927 líneas, 16 secciones + 3 anexos) se corrompió 3× por truncamiento de `write_file` antes de reconstruirse limpiamente con el patrón `execute_code` + `open().write()`. Tratar cualquier entregable de un solo archivo por encima de ~50KB como \"reescribir, no parchear\".\n\n---\n\n## Control de Calidad\n- Un único archivo Markdown autocontenido al final de cada sesión.\n- Cada sección que el usuario pidió añadir está presente y no vacía.\n- Glosario cubre cada sustantivo propio nuevo.\n- TOC refleja con precisión títulos y números de sección.\n- Ninguna sección dice \"No aplica en este ciclo.\" cuando el usuario ha suministrado datos — esa frase está reservada para output de *diagnósticos*, no documentos de estrategia.\n\n---\n\n## Licencia\nDerivado de la práctica de workflow HSCSG / Sistema Alráico.
